# Bug Study

This directory contains tooling for scraping, classifying, and analyzing memory safety
bugs and CVEs across a set of database management systems.

The pipeline has two parallel tracks:

- **Bug track** – scrapes bug reports from upstream issue trackers and classifies them with an LLM.
- **CVE track** – downloads the full CVEProject dataset, filters by DBMS, and classifies each CVE.

Both tracks rely on a locally running `llama-server` instance for LLM-based classification.

│   │   ├── <DBMS>_rep{1,2,3}.json    # Three independent LLM classification runs
│   │   ├── matches_<DBMS>.json       # Keyword-matched bug file paths

    ├── cvelistV5-main/          # Extracted CVEProject dataset (populated by scrape_cves)
    ├── <dbms>_cves              # Per-DBMS list of matching CVE file paths (one path per line)
    ├── cve_results/             # LLM classification results and keyword match files

> results used for the paper analysis. Extract them before running the analysis scripts if

## Quick Start: `just` Recipes

All operations are driven by [`bugs.just`](bugs.just). Run `just -f bugs.just` from this
directory to list all available recipes.

### Bug Track

| Recipe | Description |
|---|---|
| `just -f bugs.just scrape_bugs` | Scrape bug reports (2015–2025) from GitHub, Jira, and MySQL bug tracker into `memsafedb_bugs/<DBMS>/` |
| `just -f bugs.just search_bugs [dbms]` | Search scraped bugs for memory-safety keywords (used internally by `run_all_bugs`) |
| `just -f bugs.just classify_bugs [files]` | Classify bug files via the LLM (reads file paths from stdin or arguments) |
| `just -f bugs.just run_all_bugs` | **End-to-end**: keyword search + 3× LLM classification for all DBMSes → `memsafedb_bugs/bug_results/` |
| `just -f bugs.just analyse_bug_results [dbms]` | Analyze classification results for one DBMS; defaults to `LevelDB` |

### CVE Track

| Recipe | Description |
|---|---|
| `just -f bugs.just scrape_cves` | Download `main.zip` from CVEProject, extract it, and generate per-DBMS `<dbms>_cves` index files |
| `just -f bugs.just search_cves [dbms]` | Search CVEs for a DBMS using memory-safety keywords |
| `just -f bugs.just classify_cves [files]` | Classify CVE files via the LLM (takes file paths as arguments) |
| `just -f bugs.just run_all_cves` | **End-to-end**: keyword search + 3× LLM classification for all DBMSes → `cve/cve_results/` |
| `just -f bugs.just analyse_cve_results [dbms\|all]` | Analyze CVE results; `all` (default) processes every DBMS and generates a cumulative report |

### Server Management

| Recipe | Description |
|---|---|
| `just -f bugs.just download_model` | Download the configured model from Hugging Face to `models/` |
| `just -f bugs.just build_docker` | Build the CUDA-enabled `llama-server-cuda` Docker image |
| `just -f bugs.just launch_server` | Download model + build image + start `llama-server` on port **8080** |
| `just -f bugs.just kill_server` | Stop the running `llama-server` container |

### CSV Export

Run these directly with Python (no `just` recipe needed — they read the existing result files):

```bash
# Export bug results per year
python3 export_bug_results_to_csv.py
# → memsafedb_bugs/bug_results_by_year.csv

# Export CVE results per year
python3 export_cve_results_to_csv.py
# → cve/cve_results_by_year.csv
```

## Result Directories in Detail

### `memsafedb_bugs/bug_results/`

Produced by `run_all_bugs`. For each DBMS:

- **`<DBMS>_rep{1,2,3}.json`** – newline-delimited JSON; each line is `{"file": "...", "classification": {...}}`.
  The classification contains `issue_type`, `is_memory_safety`, `implication`, `confidence`, and `reason`.
- **`matches_<DBMS>.json`** – JSON array of file paths that matched at least one memory-safety keyword.
- **`report_<DBMS>_part{N}.txt`** – Human-readable reports split into 3 chunks, generated by
  `analyse_bug_results.py`. Each entry shows the bug title, description, keyword match status, and
  all three LLM classifications.

### `cve/cve_results/`

Produced by `run_all_cves`. For each DBMS:

- **`<dbms>_cve_rep{1,2,3}.json`** – Same format as bug results but includes a `cve_id` field.
- **`matches_<dbms>_cve.json`** – JSON array of CVE file paths matching memory-safety keywords.
- **`reports/report_<dbms>_cve_part{N}.txt`** – Human-readable CVE reports.
- **`reports/cumulative_report.txt`** – Aggregate statistics across all DBMSes (generated when
  `analyse_cve_results all` is run).

## CSV Output Format

Both export scripts produce a CSV with identical columns:

| Column | Description |
|---|---|
| `db` | Database name (lowercase) |
| `year` | Year the bug/CVE was created/published |
| `total_bugs` | Total bugs (all 3 LLM reps agree it's a `bug`) / total examined CVEs (in 2015–2025 range) |
| `memory_safety_bugs_llms` | Bugs/CVEs unanimously classified as memory safety issues by all 3 LLM runs |
| `memory_safety_bugs_keywords` | Bugs/CVEs matching at least one memory-safety keyword |

> For bugs, `total_bugs` counts the total number of **scraped** issue JSON files in the source
> directory. For CVEs, `total_bugs` counts the total number of CVEs in the 2015–2025 date range
> from the `<dbms>_cves` index files.

Both scripts also print two summary tables to stdout:

- **Table 1** – Per-database totals (total bugs/CVEs, memory safety count, percentage).
- **Table 2** – Implication breakdown for unanimously classified memory safety bugs/CVEs.

## LLM Model Configuration

The model is configured at the top of `bugs.just` via the `model_type` variable:

```just
model_type := "gpt-oss"   # Options: "gpt-oss" | "llama4" | "llama3"
```

| `model_type` | Model | HuggingFace Repo |
|---|---|---|
| `gpt-oss` | GPT-OSS 120B Q4_K_M (default) | `unsloth/gpt-oss-120b-GGUF` |
| `llama4` | Llama 4 Scout 4-bit Q4_K_M | `glogwa68/Llama-4-scout-GGUF` |
| `llama3` | Llama 3.1 8B Instruct Q8_0 | `bartowski/Meta-Llama-3.1-8B-Instruct-GGUF` |

Models are downloaded to `/scratch/dimitrios/memsafedb/models/` via `huggingface-cli`.

To switch models, change `model_type` in `bugs.just` (or override per-run) and re-run
`just -f bugs.just launch_server`. The `model_name` and `model_repo` variables are derived
automatically from `model_type`.

## Server Setup

### Hardware

Classification runs on our server equipped with an **NVIDIA H100 GPU**. The `llama-server`
is deployed as a Docker container with full GPU pass-through.

### Starting the Server

```bash
just -f bugs.just launch_server
```

This recipe chains three steps:

1. **`download_model`** – downloads the GGUF model from HuggingFace if not already present.
2. **`build_docker`** – builds the `llama-server-cuda` Docker image from `Dockerfile`.
3. **Launch** – starts the container with the following configuration:

| Parameter | Value | Description |
|---|---|---|
| Port | `8080` | Mapped to host; classification scripts connect to `http://localhost:8080` |
| `--n-gpu-layers` | `99` | Offload all layers to GPU |
| `--ctx-size` | `131072` | Context window (128k tokens) |
| `--batch-size` | `2048` | Prompt evaluation batch size |
| `--parallel` | `16` | Number of parallel inference slots (for concurrent requests) |
| `--cont-batching` | *(flag)* | Enables continuous batching for throughput |

The server runs in detached mode (`-d`). To stop it:

```bash
just -f bugs.just kill_server
```

### API Endpoint

Classification scripts send requests to:

```
POST http://localhost:8080/v1/chat/completions
```

This is a standard OpenAI-compatible chat completions endpoint provided by `llama-server`.

## API Tokens

Put your API tokens in `tokens.txt` (one per line, `KEY=VALUE` format):

```
GITHUB_TOKEN=ghp_...
```

The GitHub token is used by `scrape_bugs.py` to raise the API rate limit from 60 to 5000
requests/hour. Jira and the MySQL bug tracker do not require authentication.

## Date Filtering

The global date range is configured in `bugs.just`:

```just
start_date_setting := "2015-01-01"
end_date_setting   := "2025-12-31"
```

This range is applied at scraping time (bugs) and at classification time (CVEs and bugs).
For CVEs, the export script additionally enforces this range when counting totals for the
summary tables.

## End-to-End Walkthrough

Complete sequence to go from nothing to all final results. Steps are ordered so that the
server can be started once and both tracks can run against it.

### 0 — Prerequisites

```bash
# Make sure you are in the bug_study directory for all commands below
cd /scratch/dimitrios/memsafedb/bug_study
```

Ensure `just`, `docker`, `python3`, and `huggingface-cli` are available.
Add your GitHub token to `tokens.txt` (see [API Tokens](#api-tokens)).

---

### 1 — Start the LLM Server

> **Skip steps 1a and 1b** if the model is already downloaded (`models/` is populated)
> and the Docker image is already built.

**1a.** *(Optional)* Download the model explicitly:
```bash
just -f bugs.just download_model
```

**1b.** *(Optional)* Build the Docker image explicitly:
```bash
just -f bugs.just build_docker
```

**1c.** Start the server (runs 1a and 1b automatically if needed):
```bash
just -f bugs.just launch_server
```

The server is now listening on `http://localhost:8080`. Verify with:
```bash
curl http://localhost:8080/v1/models
```

---

### 2 — Bug Track

#### 2a. Scrape Bug Reports

> **Skip this step** if you extracted `memsafedb_bugs/bug_list.tar.xz` — the scraped
> bug JSON files are already in `memsafedb_bugs/<DBMS>/`.

```bash
tar -xf memsafedb_bugs/bug_list.tar.xz -C memsafedb_bugs/
# — OR — scrape fresh:
just -f bugs.just scrape_bugs
```

#### 2b. Classify Bugs (keyword search + 3× LLM)

> **Skip this step** if you extracted `memsafedb_bugs/bug_results.tar.xz` — the
> `bug_results/` directory with all rep files is already present.

```bash
tar -xf memsafedb_bugs/bug_results.tar.xz -C memsafedb_bugs/
# — OR — run the full classification:
just -f bugs.just run_all_bugs
```

This writes `memsafedb_bugs/bug_results/<DBMS>_rep{1,2,3}.json` and
`memsafedb_bugs/bug_results/matches_<DBMS>.json` for every DBMS.

#### 2c. Analyze Bug Results

```bash
# Analyze all DBMSes one by one (run once per DBMS, e.g. LevelDB, DuckDB, …)
for db in RocksDB DuckDB ClickHouse MariaDB MySQL Redis LevelDB; do
    just -f bugs.just analyse_bug_results "$db"
done
```

Produces `memsafedb_bugs/bug_results/report_<DBMS>_part{1,2,3}.txt`.

#### 2d. Export Bug Results to CSV

```bash
python3 export_bug_results_to_csv.py
```

Produces `memsafedb_bugs/bug_results_by_year.csv` and prints summary tables to stdout.

---

### 3 — CVE Track

#### 3a. Fetch and Unzip the CVE Dataset

> **Skip this step** if you already have `cve/cvelistV5-main/` extracted and the
> `cve/<dbms>_cves` index files present.

```bash
# Download (~500 MB) and extract, then generate per-DBMS index files:
just -f bugs.just scrape_cves
```

If the zip is already downloaded but not yet extracted/indexed, `scrape_cves` will skip
the download automatically.

#### 3b. Classify CVEs (keyword search + 3× LLM)

> **Skip this step** if you extracted `cve/cve_results.tar.xz` — the `cve_results/`
> directory with all rep files is already present.

```bash
tar -xf cve/cve_results.tar.xz -C cve/
# — OR — run the full classification:
just -f bugs.just run_all_cves
```

This writes `cve/cve_results/<dbms>_cve_rep{1,2,3}.json` and
`cve/cve_results/matches_<dbms>_cve.json` for every DBMS.

#### 3c. Analyze CVE Results

```bash
# Analyze all DBMSes and generate the cumulative report:
just -f bugs.just analyse_cve_results all
```

Produces per-DBMS reports in `cve/cve_results/reports/` and
`cve/cve_results/reports/cumulative_report.txt`.

#### 3d. Export CVE Results to CSV

```bash
python3 export_cve_results_to_csv.py
```

Produces `cve/cve_results_by_year.csv` and prints summary tables to stdout.

---

### 4 — Stop the Server

```bash
just -f bugs.just kill_server
```
